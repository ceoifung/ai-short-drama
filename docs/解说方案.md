# 短剧解说视频自动制作 · 方案设计（定稿）

> 需求：输入 30+ 集、单集 1-2 分钟的短剧 → AI 逐集分析提取剧情 → 撰写爆款解说文案
> → 用原剧画面 + 配音 + 字幕，本地 ffmpeg 剪出 5-10 分钟解说样片（"一口气看完"式）。不涉及 AI 生成视频。
> 形态：并入 ai-short-drama 技能（复用 whisper/ffmpeg/审核框架），新增 `mode=recap` 工作流分支。
>
> **已确认输入规模**：30+ 集 × 1-2 分钟 ≈ 全片 45-60 分钟素材，压到 5-10 分钟成片（压缩比 6-10 倍），
> 每集解说配额约 15-30 秒。以下设计均按此规模定参。

---

## 一、先定义"爆款解说片"的构成（决定流水线要产出什么）

```
音频轨:  解说口播(TTS)贯穿全片 —— 原剧对白只在"高能名场面"短促保留原声(每次≤5秒)
画面轨:  原剧切片, 按解说内容匹配(说谁给谁, 说哪场切哪场)
字幕:    解说词大字幕逐句烧录(抖音解说标配); 原声段显示台词小字幕
结构:    0-5s 高能钩子(剧透最炸画面+"这部剧太敢拍了") → 人设速览(1-2句立住角色)
         → 冲突分段推进(每30-60秒一个爆点) → 高潮原声留白 → 结尾钩子(关注看下集/评论区评理)
节奏:    中文口播约 4.5字/秒 ⇒ 5分钟≈1400字, 8分钟≈2200字, 10分钟≈2800字
```

## 二、流水线（6 阶段）

### Stage 0 · 剧集入库（确定性脚本）
- 输入：一个文件夹（ep01.mp4, ep02.mp4…任意命名，自然排序）。
- 每集：ffprobe 时长/分辨率 → 本地 faster-whisper 转写（带时间戳）→ 存
  `00_episodes/epNN/transcript_timed.txt` + `meta.json`。
- **抽帧目录**：每集按 1 帧/10s 存 JPEG（`frames/`），供分析师按需看画面而不必整集读视频（省 token、绕开视频大小限制）。

### Stage 1 · 批量剧情分析（fan-out：约 6 个"分析师"，每人 5-6 集）
- 单集 1-2 分钟的转写稿只有 300-600 字，一集一个 agent 太碎且丢失跨集连贯性——
  **按 5-6 集分批**，每个分析师读批次内全部带时间戳转写稿 + 该批次抽帧（关键处看图），
  输出每集的 **beat timeline**：
  ```
  {ep, characters:[…], 本集一句话, beats:[{t_start, t_end, 事件一句话, 冲突强度1-5, 出场人物}],
   高能时刻:[{t_start,t_end,是什么,为何炸}], 金句台词:[{t, 说话人, 台词}]}
  ```
- **beat 是全片的地基**：后面选画面全靠它的时间戳精度（whisper 句级时间戳，粒度约 10-30s）。
- 30 集全部入库转写：GPU whisper 全程约 2-3 分钟；抽帧 1张/10s ≈ 全剧 270-350 张。

### Stage 1.5 · 全剧梳理（1 个"梳理师"）
- 30 集的 beat 量（约 300 条）对文案主笔太重——先由梳理师把全部 beat 压成**故事弧大纲**：
  人物关系表 / 三幕式主线（设定→升级→高潮）/ 十大爆点排序 / 全剧金句 TOP5。
- 这一步同时决定**详略分配**：开局设定约 2 分钟、中段冲突推进约 4-5 分钟、高潮收束约 1-2 分钟，弱集合并讲（"接下来的三集都在讲…"是爆款解说的合法节奏）。

### Stage 2 · 解说文案（1 个主笔 + 审核循环，复用既有审核框架）
- **解说文案师**：读故事弧大纲（而非全量 beat）→ 撰写"一口气看完"式全文（默认目标 8 分钟 ≈ 2200 字，
  可参数调整 5-10 分钟），写入 `01_script/recap.md`（含段落标记、原声插入点建议、每段预估秒数、
  集数标注供规划师对位）。
- **文案审核官** rubric：钩子前5秒是否抓人；字数与目标时长匹配（±10%）；每集配额合理（重要爆点集可多给，
  弱集合并）；每段都有画面可配（不能写"画面里没有的东西"）；原声引用克制（单次≤5s、总时长<15%）；合规。
- 不合格带意见打回，最多 2 轮（与现有剧本审核同构）。
- ⏸ **检查点**：文案给用户过目（这是全片灵魂，必须拍板）。

### Stage 3 · 素材规划（"镜头匹配师"agent + 确定性门禁）
- 把文案切成 narration 段落，逐段匹配原剧素材，输出 `02_plan/plan.json`：
  ```
  segments:[{id, narration_text, est_seconds,
             source:{ep, t_start, t_end},        // 取自 beat timeline
             audio_mode:"voiceover"|"original",  // 解说覆盖 or 保留原声
             原声台词文本?}] 
  ```
- **机检门禁（新脚本 plan_check.py）**：① 每段素材时长 ≥ 解说音频时长（不足即报错）；
  ② 引用时间段与 beat 时间戳对齐（不凭空造时间）；③ 总时长落在 5-10 分钟；
  ④ 相同素材重复使用≤2次；⑤ 原声段单独校验时长上限。退出码=门禁，不过打回规划师（同 render_pack 模式）。

### Stage 4 · TTS 配音（唯一的外部依赖，三层策略）
- **默认 edge-tts**（微软免费接口，`zh-CN-XiaoxiaoNeural` 等音色，质量足够样片），逐段生成
  `02_plan/audio_NN.mp3`，**用真实音频时长回写 plan.json**（音频驱动时间线，杜绝声画错位）。
- **可配置**：config.json 加 `tts: {provider: "edge"|"volc", voice: …, key: …}`（火山 TTS 走已有 ark key 生态）。
- **兜底**：TTS 全不可用时→生成"静音版样片 + 完整配音稿 + 逐段字幕"，用户可自己录或丢剪映一键配音。流水线不因 TTS 挂掉而中断。

### Stage 5 · 渲染合成（确定性脚本 render_recap.py，纯 ffmpeg）
```
每段:  ffmpeg 切源片段(重编码统一 1080P/30fps/原比例)
  ├─ voiceover 段: 画面(原剧,音量压到15%垫底或静音) + TTS音频 + 烧解说大字幕(ASS,大字号描边)
  ├─ original 段:  保留原声 + 台词小字幕 + 解说静默
  └─ 段间: 0.3s 交叉淡化或硬切(爆款解说标配快切,默认硬切)
全局: amix 各段音频(解说轨/原声轨/可选BGM轨 sidechain 压缩闪避) → concat → 07_final/recap_v1.mp4
字幕: 由文案+段落时长生成 ASS(样式: 底部大字幕/顶部标题位), ffmpeg libass 烧录
BGM: 可选, 02_plan/bgm.mp3 由用户放入, 无则跳过
```
- 中间产物全落盘（每段切片、每段音频、ASS 文件），单段可重渲。

### Stage 6 · 终检（agent + 机检）
- 机检：成片时长/分辨率/音轨存在；逐段边界抽查音画同步（TTS 段的音频时长 vs 实际段落时长）。
- 视觉抽检员：看成片（分段读或抽帧对比 plan）——字幕是否压脸、钩子段画面是否最炸、原声段是否有声。
- 问题段进入"单段重做清单"（改 plan 或换素材），支持只重渲坏段。

## 四、关键设计决策（为什么这样做）

1. **音频驱动时间线**：先 TTS 后定每段画面时长，字幕按音频逐句对齐——声画错位是解说片最大废片源，从流程上杜绝。
2. **beat timeline 是精度根基**：画面匹配精度 = whisper 时间戳精度（句级，足够）。30 集按 5-6 集分批分析，
   批内共享上下文保证跨集连贯，会话数从 30 降到 6。
3. **梳理师垫在主笔前面**：300 条 beat 直接喂主笔会写散——先压成故事弧+十大爆点，主笔只跟弧走。
4. **原声克制**：爆款解说的原声是调味（名场面），不是搬运。机检硬约束时长占比，保护原创度。
5. **TTS 三层策略**：样片阶段 edge-tts 免费；商用换火山；断网静音兜底不阻塞。

## 五、默认参数（全部可配置，不再向你追问）

| 参数 | 默认值 | 配置方式 |
|---|---|---|
| 成片时长 | 8 分钟（区间 5-10） | 工作流参数 target_minutes |
| 画幅 | 跟随原剧（短剧通常 9:16），统一 1080×1920 | 自动探测 |
| 解说结构 | "一口气看完"全剧透 + 结尾关注钩子 | 提示词 p5 |
| TTS 音色 | 女声晓晓（zh-CN-XiaoxiaoNeural），可换男声云希 | config.json tts.voice |
| 原声策略 | 单次≤5s、总占比<15%，只留名场面 | plan_check 硬约束 |
| 字幕 | 底部大字幕（白字黑边），样式可调 ASS | render 参数 |
| BGM | 可选：放入 02_plan/bgm.mp3 即启用，音量自动压解说闪避 | 文件即开关 |
| 剪切节奏 | 硬切为主（爆款标配），原声段前后 0.2s 缓冲 | 默认 |

## 六、风险与边界（如实）

- **TTS 在线依赖**：edge-tts 是非官方免费接口，偶尔失效——三层策略已覆盖，失效即静音版+配音稿。
- **画面匹配精度**：beat 之外的情绪画面可能切得"不够准"（说了悲伤但画面是中性）。缓解：高能时刻由分析师显式标注冲突强度，规划师优先选高能段；终检抽查。
- **抖音原创性**：解说+原创文案属二次创作，但纯原声过多有限流风险——机检已约束占比，最终发布策略由用户把握。
- **成片体积**：8 分钟 1080P 约 150-250MB，质检 agent 不能整片直读（30MB 上限）——按段抽检 + 抽帧比对，不全片看。
- **成本**：6 批分析 + 1 梳理 + 2-3 文案审核 + 1-2 规划 + 2-3 终检 ≈ **15 个 agent 会话/一次全流程**，
  加 30 集转写（GPU 约 3 分钟），一次样片成本很低。
- **30 集文件名规范**：任意命名均可（自然排序后按序号归位），但要求**集数顺序正确**（文件名排序=剧情顺序），错序会导致 beat 时间轴对不上剧情。

## 七、实施顺序（两步走）

1. **MVP（先跑通无声链路）**：Stage 0/1/1.5/2/3 + 渲染（无 TTS，字幕版样片）——验证画面匹配与节奏，半天可出第一条样片。
2. **完整版**：加 TTS + 原声段 + BGM + 终检循环。
